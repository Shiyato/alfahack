# ADR-004. Алгоритм роутинга

**Статус:** принято · **Разделы:** §3.3.6, §3.3.6.3c, §3.3.6.8

## Контекст

Существует фундаментальный конфликт: cache affinity максимизирует
переиспользование KV-кэша, но перегружает инстанс с горячим префиксом;
балансировка даёт ровную нагрузку, но разбрасывает общие префиксы.

Сверх того, до старта неизвестно, **какие сигналы будут доступны** от
апстрима (§1.3 п. 2). От этого зависит применимость целых классов
алгоритмов.

## Решение

Контракт роутера — **интерфейс, а не алгоритм**. Четыре реализации,
выбор строкой в `config/models.yaml`, смена без передеплоя:

| Стратегия | Требуется | Когда |
|---|---|---|
| `least_load` | только нагрузка | апстрим непрозрачен, префиксы разнородны |
| `consistent_hash` | идентификатор сессии | запасной вариант, реализуется за час |
| `session` | номер хода из тела запроса | **по умолчанию** |
| `dualmap` | метаданные KV-кэша | если окажутся доступны |

## Почему сессионная основная

Она требует только номера хода, а он извлекается из `messages` любого
OpenAI-совместимого запроса — то есть работает **без какой-либо видимости
внутрь апстрима**. При этом по замеру (Б-3) даёт 92,0% попаданий при
CV 0,58 против 81,7%/0,17 у least-load: берёт почти весь выигрыш
`consistent_hash` по кэшу при вдвое меньшем перекосе нагрузки.

## Честная оговорка

По замеру Б-3, **при тесном кэше апстрима все четыре стратегии одинаковы
в пределах процентного пункта**: если блоки вытесняются раньше, чем сессия
вернётся, переиспользовать нечего. Роутер имеет смысл только потому, что
агентская нагрузка даёт высокую общность префикса.

На хакатоне первым делом надо измерить режим кэша, а не писать роутер.

## Последствия

- Стратегия — точка вариативности, а не решение, принятое вслепую.
- `dualmap` остаётся за флагом: на нашем профиле преимущества над
  least-load не показал, продавать его нечем.
