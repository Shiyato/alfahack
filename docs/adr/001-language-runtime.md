# ADR-001. Язык и рантайм

**Статус:** принято
**Дата:** 2026-09-12
**Разделы документа:** §2.1.2 (бюджет накладных расходов), §6 (структура), §8 (границы MVP)

## Контекст

Срок на хакатоне — двое суток, подготовка — девять. Объём MVP (§8) — десять
пунктов, из которых большая часть это логика принятия решений, а не
перекладывание байтов. Ориентир по объёму кода для роутера такого класса —
тысячи строк (§3.3.8.1).

Возражение, которое требовалось проверить: «прокси высоконагруженный, значит
нужен компилируемый язык». Это гипотеза, а не измерение, поэтому решение
принималось после замера, а не до него.

Бюджет из §2.1.2: грамотный гейтвей в том же сетевом регионе добавляет
**5–20 мс**. Это и есть критерий приёмки.

## Что измерено

Стенд: мок-апстрим на Go, измеритель на Go, прокси на Python
(FastAPI + uvicorn + uvloop + httptools), один воркер. Вход 2048 токенов,
выход 6 токенов, каждый прогон с уникальной солью (холодный кэш).
Воспроизводится: `loadtest/spike-sweep.sh`.

**Накладные расходы прокси (TTFT через прокси минус TTFT напрямую), мс:**

| Конкурентность | ASGI без апстрима | aiohttp + полный разбор кадров | httpx |
|---:|---:|---:|---:|
| 1   | +0,4 (p95) | **+0,3 / +1,0** | +1,3 / +3,8 |
| 50  | +1,4 / +4,8 | **+5,0 / +7,9** | +107 / +1166 |
| 200 | +3,0 / +8,1 | **+6,9 / +58,5** | +1625 / +3989 |
| 500 | +17,3 / +82,3 | **+80,6 / +180,5** | +1737 / +4825 |

*(значения p50 / p95; базовая линия напрямую в мок — TTFT p50 ≈ 20 мс на всех уровнях)*

## Три вывода, которые дал замер

1. **Язык не является узким местом.** Полный разбор каждого SSE-кадра с
   пересборкой JSON стоит ~0,3 мс к TTFT и ~0,05 мс на токен. Слой ASGI
   (uvicorn + uvloop + httptools) держит 200 одновременных стримов с
   накладными расходами 3 мс. Довод «Python медленный» на этих данных
   не подтверждается.

2. **Узкое место — HTTP-клиент, и разница между библиотеками на два порядка.**
   httpx на 50 одновременных стримах даёт p95 +1166 мс при загрузке CPU 58% —
   то есть он не упирается в процессор, а сериализует работу внутри себя.
   aiohttp на той же нагрузке даёт +7,9 мс. Это самое важное техническое
   решение стека, и оно не про язык.

3. **Потолок одного процесса — порядка 200 одновременных стримов.** До c=50
   укладываемся в бюджет и по p50, и по p95. На c=200 p50 ещё в бюджете
   (6,9 мс), но p95 уже нет (58 мс). На c=500 выходим из бюджета полностью.

## Решение

**Data-plane пишем на Python** (FastAPI + uvicorn + uvloop + httptools),
**HTTP-клиент к апстримам — aiohttp, не httpx.**

**Компоненты стенда пишем на Go:** мок-апстрим и измеритель. Граница между
языками проходит строго по процессам, которые и так раздельны, поэтому
никакого лишнего сетевого перехода в горячем пути не появляется.

Масштабирование внутри машины — несколькими воркерами uvicorn за nginx.
Это не обходной манёвр, а то же требование, что уже стоит в §3.1:
data-plane обязан быть stateless.

## Последствия

- Логика MVP (admission control, роутер, квоты, политики) пишется и
  переписывается быстро — это главный ресурс на двухсуточном хакатоне.
- **Запрет на httpx в горячем пути.** Он допустим только в control-plane,
  где запросы редки.
- Многопроцессность делает общими состояниями token bucket, таблицу
  «префикс → апстрим» и счётчики in-flight. Это та же проблема, что уже
  создана требованием §3.3.8.1 (два экземпляра прокси), и ответ тот же:
  состояние мягкое и восстанавливаемое. См. ADR-020.
- Если замер под реальной нагрузкой покажет выход за бюджет при доступном
  числе ядер, переписывается **только** stream pipeline — единственная
  часть, где стоимость на токен имеет значение. Остальное остаётся.

## Честные ограничения замера

Всё измерено на одной машине (10 ядер), где мок, измеритель и прокси
делят процессор. На c=500 базовая линия сама начинает деградировать, то
есть часть эффекта — это насыщение стенда, а не прокси. Числа годятся для
**сравнения вариантов между собой** и для выбора стека; как абсолютные
значения ёмкости они не годятся. Абсолютные цифры снимаются на разнесённых
хостах — задача отдельного прогона.
