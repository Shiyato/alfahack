# ADR-014. Главная целевая метрика

**Статус:** принято · **Разделы:** §2.1.2, §2.1.3

## Решение

Главная метрика — **goodput**: запросы, полностью завершённые в пределах
SLO. TTFT и TPOT остаются ограничениями, а не целями.

## Почему

Суммарная latency для LLM бессмысленна: она пропорциональна длине
ответа, которую мы не контролируем.

В goodput засчитываются только **полностью завершённые** запросы. Если
запрос отвалился на полпути, все потреблённые токены и занятые ресурсы
списываются впустую. Отсюда прямое правило: не начинаем то, что не
сможем закончить, — и admission control из защитного механизма на краю
превращается в оптимизатор полезной работы.

Для агентской нагрузки TTFT ослаблен: агент действует по полному ответу
и ему безразлично, когда пришёл конкретный токен. Поэтому класс
`interactive` разделён на человеческий и агентский.

## Как это меняет код

- `StreamResult.goodput_counted` требует одновременно `finished` и
  отсутствия разрыва клиентом.
- Метрика `gateway_goodput_total` инкрементируется только при соблюдении
  TTFT-SLO.
- Разрыв клиентом обязан отменять запрос к апстриму, иначе брошенная
  генерация жжёт ёмкость и не попадает в goodput ни при каком исходе.

## Ловушка измерения, в которую я попал

При симуляции goodput сначала считался по нагрузке **в момент приёма**
запроса. Это неверно: запрос обслуживается позже, и судьбу его решает
нагрузка во время обслуживания. По такой мерке наивный контур выглядел
лучшим, хотя принимал втрое больше работы, чем система способна
доделать. Правильная мерка — сквозная задержка каждого запроса.
