# ADR-005. Модель квотирования: токены против запросов

**Статус:** принято · **Разделы:** §3.3.3.5

## Решение

Квоты считаются **по токенам и по запросам одновременно**, окно —
token bucket. Списывается оценка на входе, корректируется по факту
на выходе.

## Почему

Ограничение по RPM не отражает риск: запрос с контекстом на 100 тысяч
токенов и запрос на 200 нагружают систему на два порядка по-разному.
Счёт запросов при этом тоже нужен — он ловит шквал лёгких запросов,
который по токенам выглядит безобидно.

Token bucket, а не окно: агентская нагрузка принципиально всплесковая —
агент выпускает серию запросов подряд по мере обхода инструментов, и
fixed window резал бы легитимные серии.

Предварительное списание обязательно. Без него квота не защищает вовсе:
все параллельные запросы пройдут проверку раньше, чем завершится хоть
один.

## Последствия и урок

**Числа нельзя брать «на глаз» — интуиция промахивается на два порядка.**
Первая версия конфига задавала 500 000 токенов в минуту. Число выглядит
внушительно, но при средней длине агентского запроса в 8800 токенов даёт
**0,9 запроса в секунду**. Под нагрузкой гейтвей отдавал 429 из-за
собственных квот, а не из-за перегрузки.

Правило записано в самом конфиге:
`квота = целевые_rps × средняя_длина_запроса × 60`.

**Квота защищаемого класса должна быть не меньше, чем у батча.** Иначе
интерактивный класс упирается в собственный лимит раньше, чем в ёмкость,
и под перегрузкой получает хуже батча — приоритетная очередь не успевает
ничего защитить. Разделение обязанностей: квота против злоупотребления,
очередь против конкуренции за ёмкость.
