# Высоконагруженный прокси для LLM — базовый теоретический документ

**Версия:** 0.6 (DualMap, Mooncake, SMetric, SkyLB + практика вендорских шлюзов)
**Назначение:** источник истины для сборки GitHub-шаблона репозитория.
**Статус разделов:** `[ЗАФИКСИРОВАНО]` — можно кодить · `[ГИПОТЕЗА]` — требует подтверждения · `[ПУСТО]` — ждёт материалов.

## 0. Как пользоваться документом

Документ описывает **что** мы строим, **зачем** каждый элемент нужен и **какой измеримый результат** он даёт. Код в репозитории должен быть трассируем до пунктов этого документа: каждый модуль ссылается на раздел, каждый раздел — на метрику, которая доказывает, что он работает.

Правило: **если элемент архитектуры нельзя привязать к метрике — он не попадает в MVP.** На хакатоне это единственный способ не утонуть в интересных, но недоказуемых решениях.

## 1. Постановка задачи

### 1.1 Формулировка кейса `[ЗАФИКСИРОВАНО]`

> Высоконагруженный прокси для LLM. Выстроить взаимодействие с моделью так, чтобы данные обрабатывались на лету — без шаблонов, с полным погружением в контекст задачи.
> - **Архитектура:** выдержать SLA по времени отклика, сохранив отказоустойчивость и масштабируемость сервисов
> - **Гибкость:** адаптировать систему к возможным изменениям
> - **Масштаб:** заложить кратный рост нагрузки в перспективе

### 1.2 Расшифровка требований

| Требование кейса | Как читаем инженерно | Чем доказываем |
|---|---|---|
| SLA по времени отклика | TTFT p95 и межтокенная задержка (ITL) под целевой нагрузкой | Графики TTFT p50/p95/p99 vs RPS |
| Отказоустойчивость | Отказ любого апстрима не роняет сервис | Chaos-сценарий: убиваем апстрим, смотрим error rate |
| Масштабируемость | Горизонтальная, stateless-инстансы | Замер: 1 инстанс → N инстансов, рост throughput близок к линейному |
| Гибкость | Новая модель/провайдер без передеплоя | Демо: hot-reload конфига в прямом эфире |
| Кратный рост | Нет узких мест с O(n²) и глобальных локов | Профиль под нагрузкой x10 |
| «На лету, без шаблонов» | `[ГИПОТЕЗА]` потоковая обработка без буферизации ответа целиком | См. 1.3 |

### 1.3 Открытые вопросы `[ГИПОТЕЗА]`

Заполнить после Q&A с менторами. До этого — реализуем по трактовке «по умолчанию».

1. **«Без шаблонов, с полным погружением в контекст»** — три трактовки:
   - (а) стриминговая обработка вместо батчевой;
   - (б) потоковая трансформация тела запроса/ответа (маскирование PII, инъекция контекста) без буферизации;
   - (в) отказ от заготовленных ответов в пользу реального прохода в модель.
   *Трактовка по умолчанию: (а) + (б).*
2. Мы проксируем **к** платформе как к апстриму или строим **замену** её API?
3. Целевые числа: RPS, токенов/сек, p95 — заданы организаторами или мы формулируем сами?
4. Допустим ли заранее подготовленный каркас и внешние библиотеки?
5. Формат сдачи: репозиторий / деплой / демо. Есть ли автоматическая проверка первого этапа?

## 2. Целевые показатели (SLO)

### 2.1 Почему обычные метрики не работают

Для LLM **суммарная latency бессмысленна** — она пропорциональна длине ответа, которую мы не контролируем. Запрос на 20 токенов и на 2000 токенов несравнимы. Поэтому измеряем:

| Метрика | Что это | Почему важна |
|---|---|---|
| **TTFT** (Time To First Token) | от приёма запроса до первого токена в стриме | это и есть «отзывчивость» с точки зрения человека |
| **ITL / TBT** (Inter-Token Latency) | средний интервал между токенами | определяет «скорость печати», рвань в стриме заметна глазом |
| **Gateway overhead** | наше время минус время апстрима | единственная метрика, за которую отвечаем мы |
| **Goodput** | запросов/сек, уложившихся в SLO | throughput без учёта SLO обманчив: можно обслужить всех плохо |
| **Queue time** | ожидание в очереди до отправки в апстрим | ранний индикатор перегрузки |
| **Effective Request Capacity** | доля запросов, уложившихся в TTFT-SLO | главная метрика сравнения стратегий роутинга |
| **CV (load balance ratio)** | коэффициент вариации нагрузки по инстансам | численно доказывает отсутствие перекоса |

**Определения, взятые из DualMap (см. §9):**

- *Effective Request Capacity* — процент запросов с TTFT ниже порога SLO (в их экспериментах порог 5 с). Это ровно та величина, по которой они меряют выигрыш 2,25×.
- *Goodput* — максимальная устойчивая интенсивность запросов при заданном уровне соблюдения SLO (у них — 90%).
- *CV* = σ / µ по числу pending prefill-токенов на инстансах. Ноль — идеально равномерно. У чистой cache-affinity в их замерах CV = 1,24, у DualMap — 0,00 при сопоставимом cache hit rate.

**Почему это важно для нас:** пара метрик «cache hit rate + CV» образует Парето-фронт. Один график, где наша точка лежит выше и левее всех baseline-ов, — это законченное доказательство качества роутера. Именно так построен рисунок 1 в их статье, и именно это стоит воспроизвести на защите.

### 2.1.1 Как задать SLO, не зная целевых чисел `[ЗАФИКСИРОВАНО]`

Проблема хакатона: организаторы могут не назвать абсолютные пороги, а придумывать их из головы — плохо защитимо.

**Решение из Mooncake — относительный SLO.** Запись `TTFT_P90 = 4×` означает: у 90% запросов TTFT не превысит четырёхкратного времени того же запроса, выполненного в одиночку без конкуренции. В своих end-to-end экспериментах они брали `TTFT_P90 = 10×` и `TBT_P90 = 5×`, нормируя все значения к этому потолку так, что 1.0 — граница нарушения.

**Почему это лучший вариант для нас:** порог выводится из измерения, а не назначается. Мы замеряем одиночный запрос на пустой системе, умножаем на коэффициент — и получаем защитимый SLO при любом железе и любой модели. Плюс все графики нормируются к 1.0, что делает их читаемыми без знания абсолютных величин.

**Асимметрия коэффициентов не случайна:** TTFT терпит бо́льшую деградацию, чем TBT. Рваный стрим пользователь замечает сразу, а лишнюю секунду ожидания первого токена — гораздо спокойнее.

### 2.1.3 Пересмотр: для агентской нагрузки главная метрика — не TTFT `[ЗАФИКСИРОВАНО, ревизия версии 0.2]`

Раньше в этом документе TTFT был объявлен главной целевой метрикой. Для агентской нагрузки это **неверно**, и SMetric объясняет почему.

Два свойства агентского трафика:

1. **Агент действует только по полному ответу.** В отличие от человека, который читает токены по мере их поступления, агент дожидается всего ответа, чтобы решить, какой инструмент вызвать. Ему безразлично, когда пришёл конкретный токен — первый или последний.
2. **Агент генерирует на запрос гораздо больше токенов, чем человек в чате.** Кластер должен выдерживать высокий TPS, иначе запросы встают в очередь и каждый агент ждёт дольше.

Отсюда: **основная цель — tokens per second всего кластера**, а TTFT и TPOT остаются важны, но **ослабляются, а не исчезают**. Ограничение сохраняется потому, что слишком медленный ответ агент считает таймаутом.

**Что это меняет у нас:**

| Было (версия 0.2–0.3) | Стало |
|---|---|
| Главная метрика — TTFT p95 | Главная метрика — **TPS в пределах SLO** (только те токены, что пришли с соблюдением TTFT и TPOT) |
| Оптимизируем отзывчивость | Оптимизируем пропускную способность при ограничении на отзывчивость |
| Стриминг критичен | Стриминг важен для человека, для агента — нет |

Метрика «TPS within SLO» — это clusterwide TPS, в который засчитываются только запросы, удовлетворившие и TTFT-SLO, и TPOT-SLO. Замеряется свипом по интенсивности с взятием максимума.

**Практическое следствие для классов обслуживания (§2.2):** класс `interactive` стоит разделить на человеческий (чат, стриминг в UI — жёсткий TTFT) и агентский (IDE-агент — мягкий TTFT, приоритет на пропускную способность). Это ровно наш вайб-кодинг.

### 2.1.4 Ещё один способ задать SLO

SMetric использует продакшн-таргеты, совпадающие с распространённой академической практикой: **TTFT-SLO линейный по числу входных токенов** и фиксированный TPOT-SLO (у них 30 мс).

Это третий вариант к §2.1.1, и он элегантнее: линейная зависимость от длины входа учитывает, что запрос на 100k токенов физически не может ответить так же быстро, как на 500. Единый абсолютный порог наказывает длинные запросы ни за что.

**Рекомендация:** `TTFT_SLO = a + b × input_tokens`, коэффициенты берутся из калибровочного прогона (§3.3.6.7a). Плюс фиксированный TPOT-SLO.

### 2.1.2 Goodput: считаем только доведённые до конца запросы

Тонкость, которая меняет логику всей системы. В Mooncake в goodput засчитываются **только запросы, полностью завершившие выполнение**. Если запрос отвалился на полпути, все потреблённые и сгенерированные токены не считаются, а ресурсы признаются потраченными впустую.

Отсюда прямое правило: **запрос должен быть отклонён как можно раньше, если он не сможет уложиться в SLO целиком.** Не «попробуем, а там как пойдёт», а «не начинаем то, что не сможем закончить».

Это переворачивает приоритеты: admission control (§3.3.3) перестаёт быть защитным механизмом на краю и становится оптимизатором полезной работы. Для формулировки кейса про SLA это ключевой аргумент.

**Ориентир по накладным расходам:** грамотный гейтвей в том же сетевом регионе добавляет 5–20 мс, что обычно менее 2% от общего времени запроса. Лучшие в классе показывают доли миллисекунды на p99. Наш бюджет: `[ПУСТО — зафиксировать после первого замера]`.

### 2.2 Классы обслуживания `[ЗАФИКСИРОВАНО]`

Это ядро решения. Без классов «высоконагруженность» не имеет смысла — все запросы деградируют одинаково.

| Класс | Пример нагрузки | SLO | Поведение при перегрузке |
|---|---|---|---|
| `interactive` | агент в IDE, чат | TTFT p95 ≤ X мс | защищаем в первую очередь |
| `batch` | массовая обработка, индексация | TTFT не нормируется | деградирует первым, растягивается по времени |
| `background` | прогревы, аналитика | best effort | отбрасывается при нехватке ёмкости |

**Зачем:** реальная боль, из-за которой такой прокси и пишут, — интерактивный пользователь ждёт минуты, потому что его запрос стоит в одной очереди с батчем.
**Результат:** под нагрузкой x10 `interactive` держит SLO, `batch` растягивается. Это один график, который продаёт всё решение.

## 3. Архитектура

### 3.1 Главное решение: разделение data-plane и control-plane

```
┌─────────────────────────────────────────────────────────┐
│  CONTROL PLANE (редкие операции, не в горячем пути)     │
│  реестр моделей · квоты · ключи · политики · биллинг    │
└───────────────────────┬─────────────────────────────────┘
                        │ push/watch конфигурации
┌───────────────────────▼─────────────────────────────────┐
│  DATA PLANE (горячий путь, stateless, масштабируется)   │
│  приём → auth → admission → роутинг → стрим → учёт      │
└─────────────────────────────────────────────────────────┘
```

**Зачем:** горячий путь не должен ходить в БД за конфигом на каждом запросе — это и латентность, и точка отказа.
**Результат:** (1) падение control-plane не останавливает трафик, data-plane работает на последнем известном конфиге; (2) закрывается требование «гибкость» — модель добавляется правкой конфига без передеплоя; (3) data-plane остаётся stateless и масштабируется горизонтально.

Это же разделение — стандарт индустрии: команды, строившие такие шлюзы, приходят ровно к двум слоям, где готовый прокси обрабатывает `/v1/*`, а собственная логика (биллинг, квоты) живёт отдельно.

##### 3.1.1 Декларативные политики — прямой ответ на критерий «гибкость»

Промышленные шлюзы описывают политики правилами в YAML, применяемыми из CLI и хранимыми в git. Ценность для нас в том, что это **демонстрируемо**: правка файла, применение, изменение поведения в прямом эфире, без передеплоя.

Форма правила квотирования:

```yaml
rules:
  - id: "user-gpt4-limit"
    when:
      subjects: ["user:bob@example.com", "team:backend"]
      models: ["main/gpt4"]
      metadata: { env: prod }
    limit_to: 1000
    unit: requests_per_day
```

**Семантика порядка — важная деталь с ловушкой.** Правила вычисляются по порядку, применяется первое совпавшее, поэтому специфичные правила должны стоять выше общих. Это удобно и привычно (как ACL или правила файрвола), но **порядок становится частью семантики**: перестановка строк молча меняет поведение. Обязательно нужен валидатор конфига, который предупреждает о недостижимых правилах — тех, что полностью перекрыты вышестоящими. Стоит полчаса, а на защите отвечает на вопрос «а как вы гарантируете корректность политик».

**Что берём в шаблон:** `config/ratelimit.yaml`, `config/fallback.yaml`, `config/models.yaml`, все под hot-reload, все версионируются. Демо-сценарий: добавляем модель и меняем квоту прямо во время показа.

### 3.3 Компоненты

#### 1. Edge / API-слой

**Что:** HTTP-эндпоинт, OpenAI-совместимый (`/v1/chat/completions`, `/v1/embeddings`, `/v1/models`), SSE для стриминга.
**Зачем именно OpenAI-формат:** это де-факто стандарт. Любой существующий клиент — плагин в IDE, Open WebUI, SDK — начинает работать без единой строки правок. На демо это бесплатный вау-эффект: подключаем реальный редактор кода к нашему прокси.
**Результат:** нулевая стоимость интеграции, совместимость с экосистемой, отсутствие вендор-лока.
**Внутри:** сразу нормализуем в собственный доменный формат — иначе логика роутинга прирастёт к формату конкретного провайдера и требование «гибкость» умрёт.

#### 2. Auth & tenant resolution

**Что:** виртуальный ключ → тенант, команда, класс обслуживания, лимиты, разрешённые модели.
**Зачем:** без понятия тенанта невозможны ни квоты, ни приоритеты, ни учёт стоимости. Виртуальные ключи также решают энтерпрайз-задачу: реальные ключи провайдеров не покидают гейтвей.
**Результат:** мультитенантность, отзыв доступа без ротации провайдерских ключей, атрибуция расходов.
**Реализация:** резолвинг из in-memory кэша, наполняемого control-plane. В горячем пути — ноль сетевых вызовов.

#### 3. Admission control (ключевой блок)

**Что:** решение «принять / поставить в очередь / отказать» до отправки в апстрим.

**Три механизма:**

- **Квоты по токенам, а не по запросам.** Ограничение по RPM не отражает реальный риск: лимиты должны считать токены, стоимость и конкурентность на пользователя, команду и модель. Запрос с контекстом на 100k токенов и запрос на 200 токенов нагружают систему на два порядка по-разному. Алгоритм: token bucket, пополняемый по токенам; списание — предварительная оценка на входе, корректировка по факту на выходе.
- **Приоритетная очередь** по классам обслуживания (см. 2.2) с fair-share между тенантами внутри класса — чтобы один шумный сосед не съел весь класс.
- **Ранний отказ.** Если по текущей глубине очереди прогноз ожидания превышает SLO — отдаём 429 с `Retry-After` немедленно. Идея с научным обоснованием: в Mooncake это называется Early Rejection Based on Prediction — предсказание нагрузки после стадии префилла для отказа в перегрузке.

**Зачем:** без admission control система под перегрузкой деградирует худшим способом — все запросы висят и отваливаются по таймауту, потратив ресурсы впустую.
**Результат:** предсказуемая деградация. Честный быстрый 429 лучше таймаута на 120-й секунде — клиент может отступить или уйти в другой класс.

##### 3.1 Что считать «нагрузкой»: SLO вместо счётчика запросов

Стандартный подход — измерять нагрузку долей обрабатываемых запросов от максимальной ёмкости. Mooncake делает иначе: **использует соблюдение SLO как прямую меру нагрузки**. Задаются ограничения `l_ttft` и `l_tbt`, и загруженность инстанса определяется сравнением прогнозируемых максимальных TTFT и TBT с этими порогами.

**Почему это правильнее:** «80% ёмкости» — величина, которую невозможно честно определить для LLM, где запросы различаются на порядки. «Прогнозируемый TTFT превысит SLO» — проверяемое утверждение, напрямую связанное с тем, что видит пользователь.

**Берём в архитектуру:** метрика загруженности апстрима в нашем прокси — не число in-flight запросов, а прогноз нарушения SLO.

##### 3.2 Раннее отклонение

Логика: оценивать допустимость запроса **до начала дорогой работы**, а не после. В Mooncake это означает решение по большей из двух загрузок — пула префилла и пула декодирования, — принимаемое на входе. Если бы решение принималось после префилла, вычисления префилла для отклонённого запроса пропали бы зря.

Если SLO недостижим, Conductor **сразу возвращает HTTP 429 Too Many Requests** наверх. Ровно тот контракт, который мы закладывали в §3.3.3.

Эффект в цифрах на реальных трассах (23 000 запросов, кластер 8+8, воспроизведение с двукратной скоростью для имитации перегрузки):

| Стратегия | Отклонено запросов |
|---|---|
| Baseline (решение перед каждой стадией) | 4 183 |
| Early Rejection | 3 771 |
| Early Rejection на основе предсказания | 3 589 |

Меньше отклонений при той же ёмкости — потому что не тратится работа на запросы, которые всё равно не доедут.

##### 3.3 Ловушка: раннее отклонение вызывает автоколебания `[КРИТИЧНО]`

**Это самое ценное, что даёт Mooncake для нашей защиты, и это неочевидно.**

Наивное раннее отклонение порождает новую проблему: наблюдаемые в реальном кластере из 20 машин **противофазные колебания** загрузки. Механизм колебаний, по стадиям:

1. Загрузка низкая → принимаем много запросов, пока не упрёмся в потолок первой стадии.
2. Принятая пачка доходит до второй стадии → её загрузка взлетает → начинаем отклонять → первая стадия пустеет.
3. Новых запросов во вторую стадию не поступает → её загрузка падает → снова принимаем много.
4. Вторая стадия опять перегружена → снова отклоняем.

Корень проблемы — **лаг между предсказанием нагрузки и её фактическим возникновением**. Решение по текущей нагрузке принципиально запаздывает. Итог — качели вместо стабильной работы и плохая утилизация.

**Решение — отклонение на основе предсказания.** Предсказывается нагрузка, которая возникнет *после* завершения текущей стадии, и решение принимается по ней. Причём Mooncake сознательно выбирает **системный уровень предсказания вместо позапросного**: предсказывать длину вывода конкретного запроса дорого и неточно, особенно под перегрузкой, а оценить агрегированное состояние пула через время — проще и требует меньшей точности. Их текущая эвристика: считать время декодирования каждого запроса равным константе `t_d`, добавить в пул то, что завершит префилл к моменту t, вычесть то, что к моменту t завершится, и оценить среднее отношение TBT к порогу.

**Что это значит для нас:** любой контур с обратной связью «нагрузка → решение о приёме» без предсказания и без демпфирования будет колебаться. Это относится и к нашей приоритетной очереди. Минимальная защита в MVP:
- решение принимать по сглаженной оценке (EWMA), а не по мгновенной;
- ввести гистерезис: порог включения отказов выше порога выключения;
- на графике мониторинга обязательно показать загрузку во времени — если видна пила, механизм сломан.

**На защите это отличный слайд:** «наивное раннее отклонение даёт вот такие качели, мы добавили сглаживание и получили вот такую полку». Проблему легко воспроизвести на моке.

##### 3.5 Проектирование квот: измерения и окна

Раздел собран из практики промышленных шлюзов. Идей здесь нет, но есть готовая форма, которую не надо изобретать.

**По каким измерениям режут квоты:**

| Измерение | Зачем | Нужно ли нам в MVP |
|---|---|---|
| Пользователь / API-ключ | защита от злоупотреблений, учёт по клиентам | да |
| Команда / организация | изоляция тенантов в мультитенантной среде | да |
| Модель | 7B и 65B стоят по-разному, лимиты должны отличаться | да |
| Тип запроса | chat, embeddings, RAG имеют разные профили нагрузки | нет |
| Число токенов | точнее счёта запросов | да, основное |
| Регион / кластер | балансировка в геораспределённых системах | нет |

**Типы лимитов:** `requests_per_{minute,hour,day}` и `tokens_per_{minute,hour,day}`. Пара «токены + запросы» нужна одновременно: токены ловят тяжёлые запросы, счёт запросов ловит шквал лёгких.

**Три стратегии окна и чем они различаются** — это разменивание терпимости к всплескам против строгости:

| Стратегия | Терпимость к всплеску | Когда брать |
|---|---|---|
| Fixed window | худшая (эффект границы окна: двойная нагрузка на стыке) | не брать |
| Sliding window | средняя, дороже по памяти | для учёта расходов |
| Token bucket | лучшая, всплеск ограничен размером ведра | **наш выбор** для горячего пути |

Token bucket выбран потому, что агентская нагрузка принципиально всплесковая: агент выпускает серию запросов подряд по мере обхода инструментов. Fixed window будет резать легитимные серии.

**Порядок вычитания токенов.** Число выходных токенов заранее неизвестно, поэтому: на входе списываем оценку (входные токены + ожидаемый максимум выхода), по завершении корректируем по факту. Без предварительного списания квота не защищает — все параллельные запросы пройдут проверку до того, как хоть один завершится.

##### 3.6 Контракт отказа

При превышении лимита возвращается **HTTP 429 с заголовками**, по которым клиент понимает, как действовать: сколько осталось и когда повторять. Смысл в том, чтобы клиент мог выстроить автоматическую логику повтора, а не гадать.

Минимальный набор для нас: `Retry-After`, остаток квоты, момент сброса окна. Это дешёвая часть работы, которая заметно улучшает впечатление от системы на демо: клиент, корректно отступающий по 429, выглядит гораздо солиднее, чем сыплющий ошибками.

##### 3.7 Селективная отдача: очередь держим у себя `[ЗАФИКСИРОВАНО]`

Отдельный вопрос, который документ до сих пор обходил: **в какой момент запрос уходит апстриму.**

**Слепая отдача (blind pushing)** — маршрутизировать сразу по прибытии. Так работают round-robin, least-load и большинство прокси. Для CPU-нагрузок с однородным временем обработки это нормально. Для LLM — нет, потому что длительность запроса зависит от длины вывода, которую невозможно предсказать. Замеренное следствие: под round-robin разница в использовании памяти между двумя репликами достигает **2,64×**. Инстанс с короткой на вид очередью может обрабатывать её долго, и запросы копятся у него, пока соседи простаивают.

**Селективная отдача** — держать очередь **на самом прокси** и отправлять только тем апстримам, которые готовы принять. Если готовых нет, запрос ждёт у нас. Это гарантирует, что ни один запрос не стоит в очереди перегруженного апстрима, пока другой простаивает.

**Какой порог использовать — здесь неочевидное.** Естественная идея — ограничить число одновременных запросов на апстрим фиксированным числом. Это работает плохо: сколько запросов вмещает движок, зависит от суммарного объёма памяти под них, то есть от суммы входных и выходных токенов, а выход заранее неизвестен. На одной и той же модели и одном датасете предельное число одновременных запросов **гуляло от 20 до 50**. Любая фиксированная константа будет либо душить, либо перегружать.

**Рабочее решение — бинарный признак «есть ли необслуженная очередь».** Запрос считается pending, если он ещё не попал в батч, — а это прямо означает, что батч полон и памяти больше нет. Само наличие таких запросов используется как признак «апстрим занят», без всяких порогов. Опрашивается фоновым heartbeat-зондом.

**Результаты (в пределах одного региона, чтобы изолировать эффект):**

| Против чего | Эффект |
|---|---|
| Слепая отдача | пропускная способность ×1,27, **P90 TTFT ниже в 18,47 раза** |
| Фиксированный порог параллелизма | TTFT сопоставим, пропускная способность ×1,4 |
| Попадание в кэш | 89,86% против 68,89% у слепой отдачи |

Восемнадцатикратное снижение хвоста — это не оптимизация, а смена режима работы системы.

**Что берём мы.** Полноценно опросить внутреннюю очередь закрытого апстрима мы не сможем. Но принцип переносится целиком:

1. **Очередь живёт на прокси, а не размазана по апстримам.** Это единственный способ перераспределить запрос, который ещё не начали обрабатывать.
2. **Признак занятости — адаптивный, а не константа.** Наши доступные заменители: рост наблюдаемого TTFT выше калиброванного ожидания (§3.3.6.7a) — самый честный сигнал; счётчик in-flight токенов, а не запросов; таймауты и 429 от апстрима как явный признак.
3. **Побочная выгода:** очередь на прокси — это то место, где живут приоритеты классов обслуживания (§2.2). Без неё приоритизация физически негде реализовать. Два механизма оказываются одной сущностью.

Этот пункт стоит подсветить на защите: большинство самодельных прокси делают именно слепую отдачу, и объяснение, почему это неверно для LLM, сразу отделяет вас от них.

##### 3.4 Приоритеты

Необходимость классификации приоритетов запросов Mooncake называет открытой задачей, а разработку политики с учётом разных приоритетов и разных TTFT/TBT-SLO выносит в планы. То есть наши классы обслуживания из §2.2 — не самодеятельность, а то, чего в промышленной системе пока не хватает. Стоит это подсветить.

#### 4. Потоковая пред-обработка

**Что:** маскирование PII, инъекция системного контекста, guardrails — всё без буферизации полного тела.
**Зачем:** это прямая отработка «данные обрабатываются на лету» и одновременно энтерпрайз-требование (чувствительные данные в защищённом контуре).
**Результат:** нулевой вклад в TTFT (обработка совмещена с чтением тела), возможность работать с чувствительными данными.
**Осторожно:** любая синхронная обработка здесь попадает в бюджет TTFT. Всё, что можно сделать асинхронно (аудит, классификация) — выносим за горячий путь.

#### 5. Кэш

- **Exact-match** по хешу (модель + параметры + сообщения) — только при `temperature=0`. Дёшево, безопасно, даёт мгновенный ответ вместо полного round-trip.
- **Семантический** по эмбеддингам с порогом сходства — **опционально и с флагом отключения**.

**Зачем:** самый дешёвый способ снять нагрузку.
**Результат:** кэшированные ответы возвращаются за единицы миллисекунд против полного цикла инференса.
**Риск, который надо проговорить вслух на защите:** семантический кэш — это ровно те «шаблоны», от которых кейс отталкивается. Позиция: реализуем, но выключен по умолчанию, включается политикой на уровне тенанта, всегда помечаем ответ как кэшированный.

#### 6. Router (интеллектуальное ядро) — реализация по DualMap

**Что:** выбор конкретного инстанса/апстрима под запрос.

##### 6.0 Проблема, которую решаем

Существует фундаментальный конфликт двух целей:

- **Cache affinity** — слать запросы с общим префиксом на один инстанс, чтобы переиспользовать KV-кэш и не пересчитывать префилл. Максимизирует cache hit rate, но популярность префиксов в реальных нагрузках перекошена: горячий префикс перегружает один инстанс, остальные простаивают.
- **Load balancing** — слать на наименее загруженный. Даёт идеальный CV, но разбрасывает общие префиксы и убивает cache hit rate.

Ключевое наблюдение DualMap: **все существующие подходы работают в одном пространстве отображения** и потому вынуждены применять prompt-aware маршрутизацию к части запросов, а load-aware — к остальным. Из-за этого Preble, Mooncake (Min TTFT) и Dynamo дают промежуточный результат по обеим метрикам и не достигают ни одной цели полностью. Preble включает cache-aware режим только когда prefix hit rate превышает 50%; Dynamo и Mooncake переключаются на prompt-aware при дисбалансе и на load-aware при равномерной нагрузке.

**Почему round-robin/least-loaded не годится:** least-loaded игнорирует наличие кэша — запрос уходит на менее загруженный инстанс, хотя нужный KV-кэш лежит на соседнем, что даёт cache miss, длинный префилл, занятие ускорителя и рост TTFT у последующих запросов.

##### 6.1 Двойное отображение (ядро алгоритма)

Каждый запрос отображается **двумя независимыми хеш-функциями от префикса промпта** в два кандидата, из которых выбирается лучший по текущему состоянию системы.

Почему это разрывает конфликт:
- **Affinity:** для m запросов с одинаковым префиксом DualMap гарантирует cache hit rate `max(0, 1 − 2/m)` против `max(0, 1 − 1/m)` у чистой cache-affinity. При больших m разница исчезает.
- **Баланс:** по теореме Power of Two Choices максимальная нагрузка ограничена `m/n + log log n / log d + O(1)`. При d = 1 отклонение равно `Θ(sqrt(m·log n / n))` — растёт с m и n. При d = 2 отклонение становится `log log n`, экспоненциально меньше.

**Почему именно два кандидата, а не больше** — важный вопрос для защиты. Рост d уменьшает отклонение лишь логарифмически и быстро упирается в убывающую отдачу, зато расширяет множество кандидатов и разбрасывает одинаковые префиксы по большему числу инстансов, разрушая локальность KV-кэша. Глобальная стратегия «опросить всех и выбрать лучшего» эквивалентна d = n: выигрыша по нагрузке почти нет, а cache reuse деградирует сильно.

Техническая деталь: если обе хеш-функции дали один инстанс, второй кандидат берётся как `(instance_id1 + 1) mod n`, чтобы кандидатов всегда было ровно два.

##### 6.2 Адаптивная длина префикса для хеш-ключа

Проблема: планировщик заранее не знает длину общего префикса. Слишком длинный ключ выходит за пределы реально общего префикса и разводит запросы по разным инстансам, ломая reuse; слишком короткий — вызывает коллизии разных наборов запросов и концентрирует нагрузку.

Решение: **дерево горячести префиксов**. Хеш-ключ — путь от корня к листу. Когда лист становится горячим, добавляются дочерние узлы, удлиняя ключ и распределяя горячие запросы по большему числу инстансов; когда родитель остывает, дети удаляются, ключ укорачивается и запросы снова собираются на одном инстансе. Горячесть отслеживается по доле трафика ρ в скользящем окне: префикс горячий при `ρ > 2/n`, остывшим считается при падении до `ρ < 1/n` (гистерезис против дребезга).

Эмпирика из статьи, полезная как ориентир: на диалоговой нагрузке 95% запросов обходятся ключом в 2 блока по 512 токенов (один системный блок + один пользовательский). На агентской нагрузке 45,2% запросов используют 2 блока, но 14,9% и 37,8% — 6 и 13 блоков соответственно, из-за двух аномально популярных префиксов, которые механизм автоматически «раздвинул».

**Для нас это прямое указание:** фиксированная длина префикса — заведомо плохое решение под агентский трафик, а именно он у нас основной.

**Как технически считать ключ (схема Mooncake).** Вход режется на блоки, и для каждого блока считается хеш **от токенов блока, сцепленных с хешем предыдущего блока**. Получается цепочка, в которой каждый блок идентифицируется вместе со всей своей предысторией. Сравнение ключей запроса с ключами инстанса идёт последовательно до первого несовпадения — это и даёт `prefix_len`.

Почему цепочка, а не независимые хеши блоков: одинаковый блок в разных контекстах — это разные KV-состояния. Хеш от «блок + предыстория» решает это автоматически и заодно даёт дедупликацию. Схема простая, реализуется за час и подходит нам без изменений — она нужна и роутеру (§6.3), и кэшу (§3.3.5).

Размер блока — параметр: у Mooncake это сотни токенов, у DualMap в замерах 512 и 128 токенов в разных местах. Начать стоит с 256–512.

##### 6.3 SLO-aware выбор из двух кандидатов

Наивные варианты и почему они плохи:

- *least-loaded между двумя* — игнорирует кэш;
- *cache-affinity между двумя* — перекос нагрузки;
- *Min TTFT* (оценить `TTFT(r,i) = Tq(r,i) + Tc(r,i)` и взять минимум) — на первый взгляд оптимально, но **осциллирует**: очередь на кэширующем инстансе растёт, запрос уходит на второй с cache miss, очередь спадает, следующие возвращаются обратно. Постоянные переключения дают частые промахи кэша и в итоге ухудшают общий TTFT. Погоня за поштучным оптимумом дестабилизирует систему в целом.

**Правило DualMap:** держаться cache affinity всегда, пока это возможно, и переключаться на load-aware **только когда ожидаемый TTFT превышает SLO**. Дополнительно: при равном prefix hit rate у обоих кандидатов всегда выбирается менее загруженный.

Метрика нагрузки — **число pending prefill-токенов** на инстансе (латентность префилла масштабируется с числом токенов). Из заданного TTFT-SLO выводится `ttft_slo_threshold` — максимальное число pending prefill-токенов, которое ускоритель успевает обработать в рамках SLO. Он и служит критерием переключения.

Псевдокод для реализации:

```
candidates = [hash1(prefix_key) % n, hash2(prefix_key) % n]
if candidates[0] == candidates[1]:
    candidates[1] = (candidates[0] + 1) % n

best_cache = argmax(prefix_hit_len(c) for c in candidates)
if prefix_hit_len равны:
    return менее загруженный
if estimated_ttft(best_cache) <= TTFT_SLO:
    return best_cache          # приоритет affinity
return менее загруженный        # деградация в load-aware
```

Вклад именно этого правила по их ablation: относительно Min TTFT оно снижает P50 TTFT на 23,5% и P90 на 18,5%.

##### 6.4 Hotspot-aware ребалансировка

Даже при двойном отображении перекос популярности префиксов создаёт устойчивые горячие инстансы. Механизм вдохновлён cuckoo hashing: у каждого запроса есть две возможные «ячейки», и его можно переселить во вторую.

Правила:
- миграция **только внутри пары кандидатов**, не по всему кластеру — это сохраняет affinity и держит сложность под контролем;
- выгода миграции `B(i→j) = TTFT(r,i) − TTFT(r,j)`;
- запрос мигрирует, только если `B > 0` **и** `TTFT(r,j) < TTFT_SLO`;
- запросы сортируются по убыванию выгоды и мигрируют, пока вся очередь перегруженного инстанса не начнёт укладываться в SLO;
- миграция **однораундовая, батчевая, без рекурсии** — в отличие от классического cuckoo hashing, чтобы ограничить накладные расходы.

Вклад: дополнительное снижение P90 TTFT на 11,3%.

##### 6.5 Эластичность: двойное хеш-кольцо

Статическое хеш-отображение при добавлении/удалении инстанса вызывает глобальный ремаппинг и разрушает cache affinity. Решение — совместить двойное отображение с consistent hashing: инстансы и префиксы кладутся на логическое кольцо, каждая из двух хеш-функций даёт якорь, кандидат — ближайший по часовой стрелке инстанс. При добавлении инстанса ремаппятся только запросы, попавшие в новый сектор между предыдущим и новым якорем; остальные сохраняют отображение.

**Результат в цифрах:** масштабирование 4 → 8 инстансов при перегрузке восстанавливает SLO attainment до 90% практически сразу; обратное сжатие 8 → 4 при спаде нагрузки удерживает более 90%.

Это напрямую закрывает пункт кейса про «кратный рост нагрузки в перспективе» — и, что важно, закрывает его *измеримо*.

| Операция | Стоимость |
|---|---|
| Двойное хеширование | ~0,05 мс |
| SLO-aware роутинг целиком (хеши + оценка TTFT) | ~0,6 мс на запрос |
| Запрос/сохранение метаданных KV-кэша | ~0,2 мс, не зависит от размера кластера |
| Hotspot-ребалансировка | 2,2–2,5 мс на вызов |

**Что отсюда берём:** роутинг обязан укладываться в доли миллисекунды и **не расти с размером кластера**. Достигается это тем, что решение принимается по локальным метаданным двух кандидатов, а не опросом всего пула. Ребалансировка на порядок дороже роутинга — значит, она выносится из горячего пути в отдельный периодический цикл.

##### 6.3a Сессионная маршрутизация (SMetric) — самый реализуемый для нас слой

**Почему этот подход отдельный.** DualMap и Mooncake требуют видимости состояния инстансов. SMetric требует только того, что **уже лежит в самом HTTP-запросе**. Для прокси перед закрытым API это решающее отличие.

**Наблюдение о залипании сессий.** Под cache-aware маршрутизацией **96,6% последующих запросов возвращаются на тот же инстанс, что обслужил первый запрос сессии**; под чистой балансировкой — только 4,0%. Причина цепочки: последующий запрос переиспользует KV предыдущего хода той же сессии, этот KV лежит локально на обслужившем инстансе, поэтому роутер отправляет запрос туда же.

**Вывод, из которого всё следует:** размещение **первого** запроса сессии определяет размещение всей сессии. Значит, чтобы сбалансировать кластер, достаточно балансировать только первые запросы — а это малая доля трафика.

**Алгоритм:**

```
c = prefix_hit_len(req)          # по инстансам
l = load()                        # по инстансам
s = argmax(c)                     # инстанс с наибольшим попаданием

if req.turn != 0 and not_overloaded(s, l) and session_not_evicted(req, s, c):
    route_to = s                  # залипание на сессию
else:
    route_to = argmin(load_balance_score)   # чистая балансировка

def not_overloaded(s, l):
    return l[s] <= OVERLOAD * mean(l)       # OVERLOAD > 1, по умолчанию 2

def session_not_evicted(req, s, c):
    # est_hit — ожидаемое попадание, оценённое по истории переписки
    # в самом запросе, исключая свежедобавленный ход
    return c[s] > HIT_RATIO * est_hit(req)
```

**Два предохранителя и зачем они:**

- `not_overloaded` — страховка от хвостового случая, когда две изначально короткие сессии на одном инстансе обе разрастаются и перегружают его. Тогда откат на балансировку фактически мигрирует длинную сессию. Важно: переиспользование при этом не теряется, если есть общий слой кэша.
- `session_not_evicted` — если сессия долго простаивала, её KV мог быть вытеснен. Такой запрос надо трактовать как первый запрос новой сессии. Определяется сравнением фактического попадания с ожидаемым по истории.

**Устойчивость гиперпараметров — важно для хакатона.** При изменении `OVERLOAD` от 1,0 до бесконечности TPS остаётся в пределах 6% от значения по умолчанию, при `HIT_RATIO` от 0 до 0,75 — в пределах 4%; общий hit ratio держится на 75–76%. Настройки лежат на широком плато. **Это значит, что подбирать их на хакатоне не придётся** — берём 2 и 0,5 и не тратим время.

##### 6.3b Определение номера хода без состояния — ключевой приём

Самая ценная инженерная идея статьи для нашей архитектуры.

Роутеру нужен номер хода в сессии. Наивное решение — держать таблицу «сессия → инстанс»: она растёт с числом активных сессий, требует обновления и сборки мусора, потому что сессия никогда не сообщает о своём завершении.

**Вместо этого номер хода выводится из самого запроса.** Поскольку LLM-API устроен без состояния, каждый запрос несёт всю предыдущую переписку сессии, и номер хода определяется прямо по количеству исторических сообщений в запросе. Роутер не хранит ничего: маршрутизация становится чистой функцией от запроса.

Вырожденный случай безопасен: если агент отбросил историю, определение не сработает, но запрос будет обработан как первый в новой сессии — а это и есть правильное решение, потому что такой запрос всё равно почти не попадёт в кэш.

**Почему это критично именно для нас.** В §6.8 мы разбирали три сценария применимости. Этот приём радикально улучшает сценарий 2: **номер хода извлекается из `messages` в теле OpenAI-совместимого запроса — то есть доступен нам всегда, независимо от того, насколько закрыт апстрим.** Мы можем реализовать полноценную сессионную маршрутизацию, не имея вообще никакой видимости внутрь платформы.

Практически: `turn = len(req.messages) // 2` с поправкой на системное сообщение, плюс хеш от истории без последнего хода как идентификатор сессии.

##### 6.3c Как соотносятся три подхода

Наши источники предлагают три разных ответа на один вопрос, и они спорят.

| Подход | Идея | Что требуется | Замеренный перекос (max/mean) |
|---|---|---|---|
| Cache affinity | всегда на инстанс с лучшим кэшем | метаданные KV | худший |
| Load-balance-only | всегда на наименее загруженный | только нагрузка | 2,0–2,1× (лучший) |
| Линейная свёртка (продакшн Bailian) | `f = (1−λ)·l̂ + λ·(1−ĉ)` | и то и другое | 3,0× |
| Мультипликативная (LMetric) | `f = (L − c) × l` | и то и другое, без подбора λ | 3,2× |
| DualMap | два хеша от префикса, выбор из двух кандидатов | метаданные KV | заявлен CV ≈ 0 |
| SMetric | первый запрос сессии — балансировка, последующие — cache-aware | только номер хода | 2,6× |

**Важное возражение SMetric в адрес DualMap и Mooncake:** существующие планировщики **чрезмерно приоритизируют** переиспользование кэша, перегружая несколько инстансов и оставляя остальные простаивать, что упирает TPS в потолок. Обратите внимание: наш §6.3 сейчас реализует именно правило «держаться affinity до нарушения SLO» — то есть попадает под эту критику. Сессионный слой её снимает.

**Второе возражение, более тонкое:** балансировка не обязана жертвовать переиспользованием, если есть **общий (глобальный) слой кэша** — промах локального слоя добирается оттуда. При полностью обеспеченном глобальном слое все стратегии достигают почти одинаковой доли переиспользования 73–75%, различаясь только тем, откуда оно берётся: чистая балансировка тянет из глобального слоя, cache-aware попадает в локальный (58% против 6% локальных попаданий).

Но и обратное верно: **одной балансировки недостаточно** — она простаивает в ожидании подкачки кэша, и при отсутствии или малом размере глобального слоя проигрывает.

**Наше решение `[ЗАФИКСИРОВАНО]`:** реализуем **сессионную маршрутизацию как основной слой** (просто, не требует внутренних метрик апстрима, устойчивые гиперпараметры), а двойное хеширование DualMap — как опциональную стратегию за флагом, если окажется, что метаданные доступны. Правило выбора из §6.3 применяем **только к последующим запросам сессии**, а не ко всем.

Это меняет §8: сессионная маршрутизация переезжает в MVP вместо двойного хеширования.

##### 6.3d Где вообще проявляется выигрыш

Отрезвляющая калибровка ожиданий: при нормальной нагрузке (1,0×) разница между всеми стратегиями — в пределах 1%, потому что у кластера достаточно запаса и ошибки маршрутизации ничего не стоят. Выигрыш появляется **у колена насыщения**: при 1,5× он составляет 15%, при 1,75× — уже 4%, а при 2,0× (тяжёлая перегрузка) все стратегии теряют TPS одинаково.

**Прямое указание для нагрузочных сценариев:** мерить надо **в окрестности колена насыщения**. Замер при низкой нагрузке покажет, что все стратегии одинаковы, и обесценит вашу работу. Замер при двукратной перегрузке — тоже. Нужен свип с поиском колена.

##### 6.3e Чем обоснован выбор ключа: данные о схожести префиксов

Схожесть префиксов определяется как `len(общий_префикс(a,b)) / min(len(a), len(b))` — нормировка на минимум даёт 1, если один запрос является префиксом другого.

Замеры на публичных диалоговых датасетах:

| Пара запросов | Схожесть |
|---|---|
| Внутри одного пользователя | 19,0–20,5% |
| Между пользователями | 2,5–8,3% |
| Внутри региона | 10,9% |
| Между регионами | 2,5% |

Схожесть внутри пользователя выше межпользовательской **в 2,47–7,60 раза**, причём соотношение зависит от нагрузки.

**Вывод:** ключ маршрутизации на основе пользователя или сессии уже даёт большую часть выгоды, даже без анализа содержимого. Это подтверждает наш выбор сессионного слоя (§6.3a) с другой стороны.

##### 6.3f Упрощённая альтернатива: consistent hashing с пропуском занятых

Самый дешёвый вариант префикс-осведомлённой маршрутизации, требующий минимума состояния: **consistent hashing по идентификатору пользователя или сессии**. Он *неявно* префикс-осведомлён — запросы одного пользователя разделяют контекст и хешируются на один апстрим, безо всякого анализа промптов.

Одно расширение делает его пригодным: **виртуальные узлы кольца пропускаются по признаку доступности** соответствующего апстрима, и алгоритм продолжает обход к следующему узлу. То есть кольцо даёт affinity, а пропуск даёт устойчивость к перегрузке. Красиво и реализуется за час.

**Три известных слабости, о которых надо знать:**

| Слабость | Цена |
|---|---|
| Межпользовательское разделение префиксов теряется | −16,49% попаданий |
| Всплеск от одного пользователя перегружает один апстрим | −7,07% |
| Разнородные паттерны внутри одного пользователя | −8,78% |

Более общий вариант — **префиксное дерево**: логический trie, где в каждом узле хранится множество активных целей, дерево строится инкрементально по обслуженным запросам, размер ограничен, вытеснение по времени вставки. Полезная деталь реализации: обход прерывается досрочно, если в текущем узле нет доступной цели, потому что множество целей в дочернем узле всегда является подмножеством родительского.

Вариант с деревом обгоняет вариант с хешированием на 1,34–8,21%: дерево адаптивнее, при низкой доле попаданий (менее 50%) оно уходит на менее загруженные цели, тогда как хеширование упорно шлёт на «свой» апстрим, пока тот доступен.

**Рекомендация для нас:** consistent hashing с пропуском занятых — как запасной вариант на случай, если сессионный слой не успеем довести. Дёшево, объяснимо, работает.

##### 6.3g Честная оговорка: когда всё это не нужно

Отрезвляющий факт из тех же замеров: среди одиночных балансировщиков **простой least-load достигает 97,38% пропускной способности** продвинутого решения — когда схожесть префиксов относительно низкая, балансировка важнее affinity.

То есть весь наш роутер имеет смысл **только потому, что агентская нагрузка даёт очень высокую общность префикса** (§5.3, более 80%). Это надо явно проговорить на защите: мы не строим сложность ради сложности, мы эксплуатируем конкретное свойство конкретной нагрузки. Если бы трафик был чатовым и разнородным, честным ответом был бы least-load в двадцать строк.

Ещё один датапоинт того же рода: универсальный облачный балансировщик показывает долю попаданий 18,08–24,30% против 36,96–46,55% у специализированного. Разница в полтора-два раза — это цена того, что обычный gateway ничего не знает про LLM.

##### 6.7a Как оценивать TTFT (модель из Mooncake)

`estimated_ttft` — центральная функция роутера, и её надо чем-то наполнить. Рецепт:

- **Время префилла** предсказывается моделью, построенной на офлайн-замерах, по двум входам: длине запроса и длине совпавшего префикса. Благодаря регулярности вычислительного паттерна трансформеров ошибка предсказания мала, если офлайн-данных достаточно.
- **Время ожидания** = сумма времён префилла всех запросов в очереди инстанса.
- **TTFT кандидатов считается параллельно**, поэтому вклад самого расчёта пренебрежим на фоне инференса.

**Практический вывод для нас:** нужен короткий калибровочный прогон, который снимет зависимость «длина входа × длина префикса → время» и сохранит коэффициенты в конфиг. Это отдельный скрипт в репозитории (`loadtest/calibrate.py`) и полчаса работы, но он превращает роутер из эвристики в измеримую модель. **Заложить в шаблон сразу.**

Важное свойство префилла, объясняющее форму модели: время префилла растёт **суперлинейно** с длиной входа (внимание квадратично, MLP линейно), тогда как декодирование сублинейно по размеру батча. Поэтому линейная аппроксимация плоха на длинных контекстах — берите как минимум квадратичный член.

Отдельно предупреждение: **предсказание времени передачи данных сложнее**, потому что зависит не только от объёма, но и от состояния сети, особенно от загруженности отправляющего узла. Если в нашей схеме появятся межузловые пересылки, закладывать точную оценку не стоит — лучше консервативную.

##### 6.7b Расхождение источников: чью сторону берём

Два наших источника прямо спорят друг с другом, и это надо понимать.

**Mooncake (Min TTFT):** для каждого кандидата оценить `TTFT = T_queue + T_prefill` и выбрать минимум. Плюс порог балансировки: если лучший удалённый префикс не больше локального переиспользуемого, умноженного на коэффициент, — предпочесть локальный пересчёт.

**DualMap возражает:** поштучная минимизация TTFT осциллирует между cache-aware и load-aware решениями, что даёт частые промахи кэша под колебаниями нагрузки и ухудшает TTFT в целом. Их правило — держать affinity, пока прогноз укладывается в SLO.

**Наша позиция:** берём правило выбора из DualMap (§6.3), а модель оценки TTFT — из Mooncake (§6.7a). Они дополняют друг друга: DualMap отвечает на вопрос «как выбирать», Mooncake — «как посчитать то, по чему выбираем».

Обратите внимание на сквозной сюжет: **обе статьи независимо натыкаются на автоколебания** — Mooncake в контуре раннего отклонения (§3.3.3.3), DualMap в правиле выбора кандидата. Устойчивость контура обратной связи важнее локальной оптимальности каждого решения. Это хороший тезис для защиты и хорошая линза для ревью собственного кода.

##### 6.7c Ожидаемый эффект от cache-aware роутинга

Эксперимент Mooncake на кластере 8+8 с воспроизведением 23 000 реальных запросов, средний TTFT:

| Стратегия | Средний TTFT |
|---|---|
| Случайный выбор | 92,07 с |
| Балансировка по нагрузке | 60,41 с |
| Cache-aware | 14,36 с |
| KVCache-centric (cache-aware + балансировка кэша) | 6,26 с |

Порядок величин между наивной и продуманной стратегией — **более чем в десять раз**. Это лучший из имеющихся у нас аргументов, зачем вообще писать роутер, а не брать round-robin.

Общие результаты платформы: прирост пропускной способности от 50% до 525% на длинных контекстах при соблюдении тех же SLO, и около 75% больше обрабатываемых запросов на реальной нагрузке.

##### 6.7d Реалистичность ожиданий по кэшу

Отрезвляющая деталь, которую стоит держать в голове и озвучить на защите: авторы отмечают, что **реальная переиспользуемость в их продакшн-трассах существенно ниже, чем в воспроизводимых опенсорс-бенчмарках**. Теоретический потолок на их нагрузках — около 50% KVCache, даже при бесконечной ёмкости хранилища и бесконечном TTFT-SLO. Но показатель сильно зависит от сценария и может достигать 90% в специфических случаях.

**Вывод для нас:** не строить всю ценность решения на cache hit rate. Наш сценарий (агентский вайб-кодинг с длинными системными промптами) — как раз из благоприятных, но заявлять надо измеренное, а не потолок.

**Честное ограничение.** DualMap — это глобальный планировщик поверх self-hosted vLLM, у которого есть видимость метаданных KV-кэша и числа pending prefill-токенов на каждом инстансе. Если наш прокси стоит перед **закрытым API платформы**, этих сигналов у нас нет, и алгоритм в исходном виде неприменим.

Три сценария:

1. **Мы видим пул инстансов и их состояние** — реализуем DualMap как есть. Максимальный результат.
2. **Апстрим непрозрачен, но их несколько** — **сценарий стал существенно лучше после внесения SMetric.** Номер хода и идентификатор сессии извлекаются прямо из тела запроса (§6.3b), поэтому сессионная маршрутизация работает без какой-либо видимости внутрь апстрима. Недостающие сигналы заменяем наблюдаемыми: вместо pending prefill-токенов — свой счётчик in-flight токенов на апстрим; вместо метаданных KV-кэша — собственная таблица «префикс → апстрим» с TTL. Это наш основной рабочий сценарий.
3. **Апстрим один и непрозрачен** — роутинг вырождается, ценность смещается в admission control, приоритизацию и кэш. В этом случае §3.3.3 становится главным блоком, а не §3.3.6.

Полезное свойство самого подхода: он **агностичен к внутренней микроархитектуре сервинга и требует только оценки TTFT для каждого кандидата**. То есть контракт роутера — одна функция `estimated_ttft(request, upstream)`, и разные её реализации соответствуют трём сценариям выше. **Это и надо заложить в интерфейс модуля.**

Отдельно: в PD-дисаггрегированных системах TTFT определяется фазой префилла, поэтому роутинг ведётся только по prefill-инстансам, а decode подключается штатным механизмом фреймворка. Нам это пригодится максимум как строчка в разделе «что дальше».

##### 6.9 Референс-реализация

Код авторов: `https://github.com/ASISys/DualMap`. Реализация выполнена как **независимый слой глобального планирования** поверх vLLM — та же архитектурная позиция, что и у нашего прокси. Стоит посмотреть на границы модуля и структуру метаданных, но копировать целиком не надо: у нас другой источник сигналов (см. 6.8).

##### 6.10 Риск безопасности: утечка промптов через общий префикс-кэш

Отдельный пункт, потому что мы строим **мультитенантный банковский** прокси, а не исследовательский стенд.

Совместное использование KV-кэша между тенантами — известный вектор атаки: разделяемый кэш позволяет по времени ответа выяснять содержимое чужих промптов (Wu et al., NDSS 2025, ссылка есть в библиографии DualMap). Логика простая: если чужой префикс уже в кэше, наш запрос с угаданным префиксом обслужится заметно быстрее. Это готовый side-channel.

**Следствие для архитектуры:** ключ префикс-affinity обязан включать идентификатор тенанта. Кросс-тенантное переиспользование кэша либо запрещено, либо разрешено явной политикой только для общих системных промптов, не содержащих данных.

**Цена:** ниже cache hit rate при большом числе мелких тенантов. Это осознанный размен, и его надо озвучить на защите — упоминание этого риска сильно отличает решение уровня «прочитал статью» от решения уровня «понимаю, что строю для банка».

#### 7. Upstream-адаптеры

**Что:** трансляция внутреннего формата в API конкретного провайдера и обратно, включая различия в стриминге, tool-calling и формате ошибок.
**Зачем:** изоляция различий провайдеров в одном слое — это и есть «гибкость».
**Результат:** новый провайдер = новый адаптер + запись в реестре, без правок роутера и остальной цепочки. Индустриальный ориентир: зрелые гейтвеи держат так 100+ провайдеров за единым интерфейсом.

#### 8. Resilience

- **Circuit breaker** на апстрим: открывается, когда p99 задержки апстрима превышает порог или растёт доля ошибок.
- **Таймауты раздельные:** на установление соединения, на TTFT, на общий стрим. Один общий таймаут — типичная ошибка: он либо режет длинные легитимные ответы, либо не ловит зависший префилл.
- **Ретраи с ограничением:** повтор возможен **только до первого отданного токена**. После — стрим не идемпотентен, повтор породит дубли. Это тонкость, которую большинство реализаций забывает, и это хороший вопрос-ответ на защите.
- **Fallback** на резервную модель с явной пометкой деградации в ответе.

**Конфигурация fallback (форма из промышленных шлюзов):**

```yaml
rules:
  - id: "main-gpt4-fallback"
    when:
      models: ["main/gpt4"]
      response_status_codes: [500, 503, 429]
    fallback_models:
      - target: azure/gpt4
      - target: local/qwen
```

Устройство: условия срабатывания (модель, метаданные запроса, источник), список кодов-триггеров, **упорядоченный** список запасных целей, применяется только первое совпавшее правило. Триггерами делают восстановимые ошибки: 429, 500, 503.

**Два предупреждения, которых в вендорских материалах нет:**

1. **Переопределение параметров при подмене модели опасно.** Шлюзы позволяют менять `temperature` и `max_tokens` при уходе на запасную модель. Технически это удобно, но семантически это значит, что клиент **молча получает ответ на другой запрос**. Для банковского контура так делать нельзя без явной пометки в ответе о том, что произошла деградация и какие параметры изменились.
2. **429 как триггер fallback конфликтует с нашим admission control (§3.3.3).** Если апстрим сказал «слишком много», а мы автоматически перекладываем нагрузку на соседа, мы просто переносим перегрузку. Fallback по 429 допустим только на апстрим с независимым пулом ёмкости, иначе получится каскад. Это ровно тот случай, где механизмы, разумные по отдельности, вместе дают лавину.

**Зачем:** отказоустойчивость из критериев кейса.
**Результат:** отказ одного апстрима даёт кратковременный рост latency вместо всплеска ошибок. Проверяется chaos-сценарием.

##### 8.1 Отказоустойчивость самого прокси `[ПРОБЕЛ, выявлен при разборе SkyLB]`

До сих пор документ описывал устойчивость к отказам апстримов и молчал о том, что **прокси сам является единой точкой отказа**. Для «высоконагруженного» решения это дыра, и её обязательно найдут на защите.

Проблема шире, чем кажется: как только у нас появляется состояние маршрутизации (таблица префиксов, счётчики очередей, кольцо), несколько экземпляров прокси начинают конфликтовать — без координации они независимо выберут один и тот же апстрим как лучший и создадут горячую точку. При этом полная синхронизация требует порядка `O(N_прокси × N_апстримов)` соединений и зондов, что не масштабируется.

**Референсное решение — двухслойная маршрутизация:** координировать трафик **между экземплярами прокси**, а не между прокси и всеми апстримами. Каждый экземпляр либо обслуживает своими апстримами, либо передаёт запрос соседнему экземпляру, который принимает решение уже внутри своей зоны. Экземпляров прокси на порядки меньше, чем апстримов, поэтому связей мало и это масштабируется.

Соответственно устроено и восстановление: контроллер по health-пробам обнаруживает отказ экземпляра и переназначает его апстримы ближайшему живому, который временно считает их своими; после восстановления они возвращаются. Поддерживается одновременный отказ нескольких экземпляров.

**Что делаем мы за два дня:**
- **Обязательно:** прокси stateless по горячему пути (§3.1), состояние маршрутизации — мягкое, восстанавливаемое, потеря экземпляра означает лишь временное падение доли попаданий в кэш, а не потерю запросов. Запустить два экземпляра за балансировщиком и показать, что убийство одного не роняет сервис.
- **Слайд «что дальше»:** двухслойная координация между экземплярами, единый контроллер, авто-восстановление.

Формулировка для защиты: «состояние маршрутизации у нас мягкое — при потере экземпляра деградирует эффективность, но не корректность». Это сильный и честный ответ.

**Полезный ориентир по объёму работ:** геораспределённый балансировщик из статьи — около 3000 строк Python поверх готового фреймворка сервинга, совместимый с любым движком с OpenAI-API. Это трезвая калибровка: продуманный роутер такого класса — тысячи строк, а не десятки тысяч. За два дня с ИИ-ассистентом MVP реалистичен.

#### 9. Stream pipeline

**Что:** SSE наружу, потоковая пост-обработка, подсчёт токенов на лету, корректная обработка разрыва соединения клиентом.
**Критично:** при отключении клиента **обязательно отменяем запрос к апстриму**. Иначе брошенные генерации продолжают жечь ёмкость — классическая утечка, которая проявляется именно под нагрузкой.
**Результат:** отсутствие «зомби-запросов», честное освобождение ёмкости, корректный ITL.

#### 10. Учёт и наблюдаемость

**Метрики (Prometheus):** TTFT/ITL по классам и моделям, gateway overhead, глубина очереди, cache hit rate, prefix hit rate, токены и стоимость по тенантам, состояние circuit breaker.

**Ключевой приём для дашборда:** разделять время пользователя и время инференса. Разница между ними — это сеть и прокси, и если она растёт, проблема не в модели, а в инфраструктуре. Именно эта разница — метрика нашей ответственности.

**Панели по квотам** (стандарт вендорских шлюзов, дёшево и хорошо смотрится): число запросов, заблокированных лимитами; топ пользователей, команд и моделей по потреблению. Первая панель показывает, не задушили ли мы легитимный трафик; вторая находит шумного соседа.

**Три графика на защиту:**
1. TTFT p50/p95/p99 против RPS — доказательство SLA.
2. Поведение при отказе апстрима — доказательство отказоустойчивости.
3. Эффект приоритизации: `interactive` держит SLO, `batch` деградирует — доказательство осмысленности архитектуры.

## 4. Матрица деградации

Явное описание того, что происходит при росте нагрузки. Наличие такой матрицы само по себе признак зрелого решения.

| Уровень нагрузки | Поведение системы |
|---|---|
| Норма | все классы в SLO |
| Повышенная | `background` отбрасывается, растёт cache hit |
| Высокая | `batch` уходит в очередь, `interactive` в SLO |
| Перегрузка | ранний 429 для `batch`, `interactive` в SLO с деградацией на резервную модель |
| Отказ апстрима | circuit breaker, весь трафик на живые апстримы, рост latency без ошибок |
| Полный отказ | 503 с понятным телом, без зависаний |

**Отдельное требование к матрице:** переходы между уровнями должны быть устойчивыми. Контур «оценка нагрузки → решение о приёме» без сглаживания и гистерезиса даёт автоколебания (§3.3.3.3). Проверяется графиком загрузки во времени под постоянной нагрузкой выше порога: должна быть полка, а не пила.

## 5. Стенд для доказательства нагрузки `[ЗАФИКСИРОВАНО]`

Без цифр слово «высоконагруженный» ничего не весит.

- **Мок апстрима — обязателен.** Заглушка, отдающая SSE с настраиваемыми TTFT, скоростью токенов, вероятностью ошибки и режимом зависания. Позволяет воспроизводимо давить систему, не трогая реальные модели и чужие лимиты.
- **Нагрузочные сценарии** (k6 / Locust): ровная нагрузка, всплеск x10, отказ апстрима, смешанный профиль классов.
- **Наблюдаемость:** Prometheus + Grafana, дашборд поднимается одной командой.
- **Профиль нагрузки** должен имитировать агентский трафик: длинный общий системный промпт + короткие пользовательские дельты. Именно на нём работает префикс-кэш, и именно так выглядит вайб-кодинг.

### 5.1 Параметры генератора нагрузки `[ЗАФИКСИРОВАНО]`

Берём характеристики реальных трасс из DualMap/Mooncake — это избавляет от спора «а откуда у вас такие числа»:

| Параметр | Диалоговая нагрузка | Агентская нагрузка |
|---|---|---|
| Средняя длина входа | 12 035 токенов | 8 596 токенов |
| Средняя длина выхода | 343 токена | 182 токена |
| Доля префикс-кэширования | 40% | 59% |

Распределение общности префикса: 48% диалоговых запросов разделяют не менее 50% своего префикса; у агентской нагрузки этот эффект сильнее — 76% запросов, из-за повторяющихся системных и инструментальных промптов.

**Три вывода для генератора:**
1. Вход на два порядка длиннее выхода. Значит, доминирует префилл, и TTFT — правильная целевая метрика.
2. Нужны два профиля: равномерный (диалог) и перекошенный, с парой аномально популярных префиксов (агенты). Второй — основной для нас и именно он ломает наивные стратегии.
3. Первые ~500 запросов — прогрев, из результатов исключаются. Иначе холодный кэш испортит все замеры.

Пороговое значение SLO для отчёта: TTFT < 5 с — так определяется SLO attainment в статье. Можно взять как отправную точку, если организаторы не зададут своё. Альтернатива, которая мне нравится больше, — относительный порог из §2.1.1.

### 5.2 Наборы профилей и модель поступления запросов

Mooncake использует четыре профиля, и такой набор стоит скопировать — он покрывает крайние случаи:

| Профиль | Вход | Выход | Доля кэша | Поступление |
|---|---|---|---|---|
| Суммаризация длинных документов | 8 088 | 229 | ~0% | Пуассон |
| Длинный контекст с повторами | 19 019 | 72 | >80% | Пуассон |
| Синтетика | 16k / 32k / 64k / 128k | 512 | 50% | Пуассон |
| Реальная трасса | 7 955 | 194 | ~50% | По таймстампам |

**Что отсюда берём:**

1. **Обязательно нужен профиль с нулевым кэшем.** Иначе мы измеряем кэш, а не роутер. Профиль с ~0% доли кэша — честная проверка, что решение не разваливается, когда переиспользовать нечего.
2. **Два режима поступления:** пуассоновский поток с управляемым RPS для параметрических замеров и воспроизведение по таймстампам для реалистичности. Первый даёт кривые «метрика против RPS», второй — правдоподобную картинку.
3. **Перегрузка имитируется ускорением воспроизведения** трассы (у них — двукратным). Проще и честнее, чем выдумывать всплеск руками.
4. Развёртка по длине контекста от 16k до 128k показывает, где решение ломается. У нас это будет один из самых убедительных графиков, учитывая суперлинейность префилла.

**Ориентир по масштабу для реалистичности сценария:** на сопоставимом мероприятии участники отправили более 96 000 запросов в чат (около 340 на человека), а в пиках нагрузка достигала 20 000 токенов в секунду.

### 5.3 Характеристики агентской нагрузки (трассы coding-агента)

Самые релевантные нам данные из всех: две трассы с продакшн-кластеров коммерческого продукта — кодового агента, снятые в пиковые часы. Наш сценарий один в один.

| Наблюдение | Значение | Следствие для генератора |
|---|---|---|
| Доля переиспользования KV | **>80%** (против 54–62% в чате) | профиль обязан иметь очень высокую общность префикса |
| Откуда переиспользование | ~67% — внутри сессии, из предыдущих ходов | генерировать многоходовые сессии, а не независимые запросы |
| Вклад системного промпта | 18–20% всех переиспользований | у всех сессий один общий системный префикс |
| Интервал переиспользования | ~90% в пределах ~100 с, P99 ≈ 841–911 с, максимум ~1,9 ч | TTL кэша порядка минут покрывает почти всё |
| Перекос сессий | верхние 25% сессий дают >80% токенов | тяжелохвостое распределение длин сессий |
| Источник запросов | **92,9–94,2% инициированы агентом**, 5,7–7% человеком | паузы между ходами короткие |
| Плотность | запросов за минуту на инстанс: в среднем 43–48, никогда не ниже 30 | конкурентных запросов много больше, чем инстансов |

**Три вывода:**

1. **Про TTL кэша.** Раз 90% переиспользований происходит в пределах ста секунд, хранить префиксы часами бессмысленно. TTL в 5–10 минут покрывает подавляющую часть выгоды при скромной памяти. Дешёвое проектное решение с хорошим обоснованием.
2. **Про балансируемость.** Несмотря на перекос сессий, нагрузка балансируется: медианный перекос по окнам 1,7 и 1,5, худшее окно ниже 2,4 и 2,1. Работает это потому, что конкурентных запросов намного больше, чем инстансов, и лёгкие запросы сглаживают тяжёлые. **Условие важное:** при малом числе одновременных запросов балансировка не спасёт. Наш профиль должен обеспечивать высокое отношение «запросов к апстримам», иначе выводы нерепрезентативны.
3. **Про генератор сессий.** Правильная форма: общий системный промпт → сессия из нескольких ходов с дописыванием истории (каждый ход расширяет предыдущий) → тяжёлый хвост по длине сессий → паузы между ходами в единицы секунд. Это принципиально другой генератор, чем «случайные независимые промпты», и без него роутер тестируется вхолостую.

Деталь про воспроизведение трасс: если модель генерирует ответы, отличные от записанных, паттерн переиспользования ломается — история последующего запроса перестаёт совпадать с закэшированным, поэтому длину ответа при воспроизведении фиксируют принудительно. Для нашего мока это тривиально, но знать надо.

## 10. Глоссарий

- **TTFT** — время до первого токена.
- **ITL / TBT** — задержка между токенами.
- **Goodput** — доля полезной пропускной способности, уложившейся в SLO.
- **Префикс-кэш (KV-cache)** — переиспользование вычислений для общего начала промпта.
- **P2C (Power of Two Choices)** — выбор лучшего из двух случайных кандидатов.
- **Admission control** — решение о приёме запроса до начала обработки.
- **Data-plane / control-plane** — горячий путь трафика / плоскость управления.
- **Cache affinity** — стратегия отправки запросов с общим префиксом на один инстанс.
- **CV** — коэффициент вариации нагрузки по инстансам, мера перекоса.
- **Effective Request Capacity** — доля запросов, уложившихся в TTFT-SLO.
- **Pending prefill tokens** — число токенов, ожидающих префилла на инстансе; прокси-метрика нагрузки.
- **PD-дисаггрегация** — разделение фаз префилла и декода по разным инстансам.
- **Consistent hashing / хеш-кольцо** — отображение, при котором добавление узла затрагивает лишь локальный участок пространства ключей.
- **Early rejection** — отклонение запроса до начала дорогой работы, если он заведомо не уложится в SLO.
- **Относительный SLO** — порог, заданный кратностью ко времени того же запроса без конкуренции (например, TTFT_P90 = 10×).
- **Блочное цепочечное хеширование** — хеш блока считается от его токенов, сцепленных с хешем предыдущего блока.
- **TPS в пределах SLO** — суммарная пропускная способность в токенах в секунду, в которую засчитываются только запросы, соблюдшие SLO.
- **TPOT** — время на выходной токен; синоним ITL/TBT в терминологии агентского сервинга.
- **Сессия / номер хода** — последовательность запросов одного агента к одной задаче; номер хода выводится из числа исторических сообщений в запросе.
- **Локальный / глобальный слой кэша** — кэш на самом инстансе против общего кэша уровня кластера; наличие второго ослабляет конфликт affinity и балансировки.
- **Колено насыщения** — область нагрузки, где стратегии маршрутизации начинают расходиться по результату.
- **Слепая отдача (blind pushing)** — отправка запроса апстриму сразу по прибытии, без проверки готовности.
- **Селективная отдача** — удержание очереди на прокси и отправка только готовым апстримам.
- **Pending-запрос** — запрос, ещё не попавший в батч; его наличие означает, что апстрим полон.
- **Схожесть префиксов** — `len(общий_префикс(a,b)) / min(len(a), len(b))`.
