# Высоконагруженный прокси для LLM

OpenAI-совместимый шлюз с приоритизацией по классам обслуживания,
кэш-осведомлённой маршрутизацией и предсказуемой деградацией под
перегрузкой.

Все числа в этом README получены замером и воспроизводятся командами из
репозитория.

## Запуск

### Весь стенд одной командой

```bash
docker compose -f deploy/docker-compose.yml up --build
```

Поднимается: четыре мок-апстрима с разными характеристиками, два
экземпляра гейтвея за nginx, Prometheus и Grafana с готовым дашбордом.

Порты настраиваются переменными окружения, если стандартные заняты:

```bash
GATEWAY_PORT=18080 GRAFANA_PORT=13000 PROMETHEUS_PORT=19090 \
    docker compose -f deploy/docker-compose.yml up
```

| Что | Адрес |
|---|---|
| Гейтвей | http://localhost:8080 |
| Grafana | http://localhost:3000 (дашборд «Высоконагруженный прокси для LLM») |
| Prometheus | http://localhost:9090 |

Проверка:

```bash
curl -X POST http://localhost:8080/v1/chat/completions \
  -H 'Authorization: Bearer sk-agent-demo' \
  -H 'Content-Type: application/json' \
  -d '{"model":"main","stream":true,"messages":[{"role":"user","content":"привет"}]}'
```

### Локально, без Docker

```bash
uv sync                                        # зависимости
(cd mock-upstream && go build -o mockup .)     # мок-апстрим
./mock-upstream/mockup -addr 127.0.0.1:9001 -id mock-a &
./mock-upstream/mockup -addr 127.0.0.1:9002 -id mock-b &
./mock-upstream/mockup -addr 127.0.0.1:9003 -id mock-c &
./mock-upstream/mockup -addr 127.0.0.1:9004 -id mock-slow -itl 25ms -concurrency 4 &

uv run uvicorn gateway.app:app --host 127.0.0.1 --port 8080 \
    --loop uvloop --http httptools
```

### Проверки

```bash
uv run pytest tests/ -q          # 220 тестов
(cd mock-upstream && go test ./...)     # 10 контрольных опытов мока
(cd loadtest/bench && go test ./...)    # 10 проверок профиля нагрузки
loadtest/e2e.sh                  # 16 сквозных проверок
```

## Соответствие требованиям кейса

| Требование | Как реализовано | Модуль | Чем доказано |
|---|---|---|---|
| **SLA по времени отклика** | TTFT-SLO линейный по длине входа; калиброванная модель времени префилла; ранний 429 вместо таймаута | `gateway/admission/`, `gateway/core/config.py` | Накладные расходы **1,2–4,1 мс** при бюджете 5–20 мс (Б-5) |
| **Отказоустойчивость** | Размыкатель по ошибкам, сериям и латентности; деградация на резервную модель; ретрай только до первого токена | `gateway/resilience/`, `gateway/stream/` | При двух мёртвых апстримах из трёх — **12 из 12 обслужены**; при убийстве экземпляра гейтвея под нагрузкой — **554 из 555** (Б-5, Б-7) |
| **Масштабируемость** | Data-plane stateless; состояние маршрутизации мягкое; два экземпляра за балансировщиком | `gateway/core/gateway.py`, `deploy/` | Под перегрузкой ×2,8 от колена — **полка 141 RPS без обвала** (Б-6) |
| **Гибкость** | Декларативные политики в YAML с hot-reload и валидатором; стратегия роутинга меняется строкой конфига | `gateway/core/registry.py`, `config/` | Смена стратегии и добавление модели **в прямом эфире за 2,5 с** (Б-5) |
| **Кратный рост нагрузки** | Кэш-осведомлённая маршрутизация; квоты по токенам; приоритетная очередь | `gateway/router/`, `gateway/admission/` | Сессионная маршрутизация: **92,0% попаданий при CV 0,58** против 81,7%/0,17 у least-load (Б-3) |
| **«На лету, без шаблонов»** | Потоковая обработка SSE без буферизации; подсчёт токенов на лету; отмена запроса при разрыве клиента | `gateway/stream/pipeline.py` | Разбор каждого кадра стоит **0,3 мс** к TTFT (Б-1) |

## Архитектура

Полное изложение — [docs/architecture.md](docs/architecture.md). Здесь —
только то, что нужно, чтобы сориентироваться.

Разделение **data-plane** (горячий путь, stateless, масштабируется) и
**control-plane** (конфигурация, редкие операции). Горячий путь не ходит
в базу за конфигом — это и латентность, и точка отказа.

Цепочка обработки:

```
приём → auth → admission → роутинг → апстрим → стрим → учёт
```

| Блок | Модуль | Раздел |
|---|---|---|
| Edge, OpenAI-совместимый контракт | `gateway/api/` | §3.3.1 |
| Виртуальные ключи, тенанты | `gateway/auth/` | §3.3.2 |
| Квоты, приоритетная очередь, ранний отказ | `gateway/admission/` | §3.3.3 |
| Маршрутизация | `gateway/router/` | §3.3.6 |
| Адаптеры провайдеров | `gateway/upstream/` | §3.3.7 |
| Размыкатель, деградация | `gateway/resilience/` | §3.3.8 |
| Потоковая обработка | `gateway/stream/` | §3.3.9 |
| Метрики | `gateway/telemetry/` | §3.3.10 |
| Реестр конфигурации, hot-reload | `gateway/core/registry.py` | §3.1 |

### Четыре стратегии маршрутизации за одним интерфейсом

До старта неизвестно, какие сигналы будут доступны от апстрима, поэтому
стратегия выбирается строкой в `config/models.yaml` и меняется без
передеплоя.

| Стратегия | Что требуется | Cache hit | CV |
|---|---|---:|---:|
| `least_load` | только нагрузка | 81,7% | 0,17 |
| `consistent_hash` | идентификатор сессии | 93,1% | 1,27 |
| **`session`** (по умолчанию) | **номер хода из тела запроса** | **92,0%** | **0,58** |
| `dualmap` | метаданные KV-кэша | 83,6% | 0,22 |

Сессионная выбрана основной: берёт почти весь выигрыш по кэшу при вдвое
меньшем перекосе нагрузки, и **не требует никакой видимости внутрь
апстрима** — номер хода извлекается из `messages`.

Честная оговорка: при тесном кэше апстрима все четыре стратегии
одинаковы в пределах процентного пункта. Роутер имеет смысл только
потому, что агентская нагрузка даёт высокую общность префикса.

## Классы обслуживания

| Класс | Пример | Поведение при перегрузке |
|---|---|---|
| `interactive` | чат с человеком | защищается в первую очередь |
| `agent` | агент в IDE | мягкий TTFT, приоритет пропускной способности |
| `batch` | массовая обработка | деградирует первым, растягивается |
| `background` | прогревы, аналитика | отбрасывается при нехватке ёмкости |

Замеренная деградация (смесь 30% interactive / 70% batch):

| Интенсивность | RPS | interactive TTFT p95 | batch TTFT p95 |
|---:|---:|---:|---:|
| 40 | 37,9 | 116 мс | 119 мс |
| 160 (колено) | 130,1 | 511 мс | 560 мс |
| 280 (×1,75) | 141,1 | **691 мс** | 907 мс |
| 400 (×2,5) | 140,8 | **651 мс** | 758 мс |

За коленом система выходит на полку вместо обвала, а интерактивный класс
держится на 14–24% лучше батча.

## Конфигурация

Все файлы под hot-reload: правка применяется за ~2,5 с без передеплоя.
Сломанный конфиг не применяется — гейтвей остаётся на последней рабочей
версии и громко сообщает об ошибке.

| Файл | Что задаёт |
|---|---|
| `config/models.yaml` | апстримы, модели, SLO, стратегия роутинга |
| `config/tenants.yaml` | виртуальные ключи, классы обслуживания, квоты |
| `config/ratelimit.yaml` | правила квотирования |
| `config/fallback.yaml` | правила деградации |
| `config/calibration.yaml` | коэффициенты модели префилла (создаётся замером) |

Валидатор предупреждает о недостижимых правилах, отсутствующем
гистерезисе, ссылках на несуществующие апстримы и о неоткалиброванной
модели там, где стратегия опирается на оценку TTFT.

## Нагрузочный стенд

```bash
# Калибровка модели времени префилла
PYTHONPATH=. uv run python loadtest/calibrate.py --url http://127.0.0.1:9001

# Агентский профиль: многоходовые сессии, общий системный промпт
loadtest/bench/bench -url http://127.0.0.1:8080/v1/chat/completions \
    -model main -auth 'Bearer sk-agent-demo' -sessions 60 -c 64 -rate 160 -d 30s

# Смесь классов — график приоритизации
loadtest/bench/bench ... -mix 'Bearer sk-chat-demo@interactive:0.3,Bearer sk-batch-demo@batch:0.7'

# Сравнение стратегий маршрутизации
PYTHONPATH=. uv run python loadtest/router_sim.py

# Контур раннего отклонения
PYTHONPATH=. uv run python loadtest/oscillation_sim.py
```

Профиль воспроизводит форму реальных агентских трасс (§5.3): общий
системный промпт, многоходовые сессии с дописыванием истории, тяжёлый
хвост по длине. На независимых промптах префикс-кэш не работает и роутер
тестируется вхолостую.

## Стек и его обоснование

**Python** для data-plane, **Go** для компонентов стенда. Граница проходит
по процессам, которые и так раздельны, поэтому лишнего сетевого перехода
в горячем пути не появляется.

Выбор сделан замером, а не по ощущению (`docs/adr/001-language-runtime.md`):

- разбор каждого SSE-кадра с пересборкой JSON стоит **0,3 мс** к TTFT —
  язык не является узким местом;
- узкое место — HTTP-клиент: на 50 одновременных стримах **httpx даёт
  p95 в 1189 мс, aiohttp — 31 мс**, разница в два порядка при загрузке
  процессора 58%. Запрет на httpx в горячем пути зафиксирован в ADR;
- потолок одного воркера — около 200 одновременных стримов,
  масштабирование горизонтальное.

## Что сделано честно, а что нет

Раздел существует потому, что решение, у которого нет границ
применимости, обычно просто не измерено.

**Измерено и воспроизводится:** накладные расходы, сравнение стратегий
маршрутизации, поведение контура раннего отклонения, качество калибровки,
деградация по классам, выживание при отказе апстримов.

**Симуляции, а не живые замеры:** сравнение стратегий (`router_sim.py`) и
контур отклонения (`oscillation_sim.py`) отвечают на вопрос «при каких
условиях механизм начинает иметь значение», а не «какие числа будут в
проде».

**Не проверено на реальном железе:** все замеры сняты на одной машине,
где мок, измеритель и гейтвей делят процессор. Числа годятся для
сравнения вариантов между собой, не как абсолютная ёмкость.

**Найденные и исправленные дефекты** описаны в `docs/benchmarks.md` — все
они были невидимы обычным тестам и найдены измерением поведения, а не
чтением кода.

**Тесты, написанные заранее для кода, которого ещё нет.** Поскольку до
старта неизвестно, к какой платформе мы подключаемся (§1.3 п. 2),
`tests/test_contracts.py` проверяет не реализацию, а **контракт** любого
адаптера и любой стратегии. Тесты параметризованы по реестрам `ADAPTERS`
и `STRATEGIES`: новый класс попадает под проверку автоматически.
